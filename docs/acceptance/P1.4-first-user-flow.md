## Supabase Data API preflight (authenticated anon JWT)

Request:

```http
GET /rest/v1/hives?select=id&limit=1
Accept-Profile: hive3
apikey: <anon>
Authorization: Bearer <anon>
```

**Result:** HTTP **406**, `PGRST106` — `Invalid schema: hive3`. Exposed schemas reported: `public`, `graphql_public`, `hive` only.

**Impact:** `apps/web` uses `client.schema('hive3').from('hives')` with the user session JWT. Hive list/create/get **cannot persist** until **`hive3` is added to Supabase API → Exposed schemas** (dashboard change on the shared project). This is not fixable in application code without violating the hive3-only data boundary or applying DDL.

Password recovery callback (2026-10-21, P1.4 defect fix): `/auth/callback` mirrors Supabase session cookies onto the redirect response, accepts `token_hash` + `type=recovery`, treats `type=recovery` as reset intent when `next` is dropped, and sets the recovery flag before `/reset-password`. After a successful reset, the user is signed out and sent to `/login?info=password_updated`.

Password reset emails use `redirectTo` **`/auth/callback?type=recovery`** (not `next=/reset-password`) so the allow list can match V3 without encoding nested paths. PKCE `code` exchanges also treat a recent `user.recovery_sent_at` as recovery when Supabase drops query params.

**Shared Supabase email template (operator, approval before change):** SSR/PKCE works best when the reset template links to `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=recovery` instead of only `{{ .ConfirmationURL }}`. That sends each app to its own `redirectTo` (V2 vs V3) and avoids the server `/auth/v1/verify` hop (email scanners can consume one-time tokens there). V2 must handle the same `token_hash` callback pattern before changing the shared template.

Not exercised in the browser here: opening a live recovery email end-to-end on Vercel after deploy. Callback intent helpers and link-error screens remain covered by unit tests.
